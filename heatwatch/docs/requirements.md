> **最重要設計原則**
> 本システムは**関係の判定装置ではなく、自分自身への早期警告装置**である。
> 出力先は常に自分ひとり。相手を評価・採点・診断せず、相手向けの出力を一切生成しない。
> パートナーへの開示、相手個人プロファイルの非永続化、ローカル完結、非難構文の禁止を、機能要件より上位の不変条件として扱う。

## 1. エグゼクティブサマリー

**定義**：自分とパートナーのInstagram DMを解析し、会話の対立温度が普段の水準から逸脱した時点で、**自分自身にのみ**通知するローカル実行型の早期警告システム。

**核となる価値**：`自分が対立に気づく時刻` より前に検知すること。この時間差（Lead Time）が正であることが、本システムの存在意義そのものである。

**非目的**：相手の評価・採点、関係性スコアの算出、会話への自動介入、相手への通知、双方調停、心理診断、長期的な関係監視ダッシュボード。

| **Go/No-Go判定** |
| --- |
| Phase 1の遡及評価において Lead Time の中央値が 0 以下（＝自覚より後にしか鳴らない）である場合、本システムに価値はない。Phase 2へ進まず終了する。 |

| 設計軸 | 採用方針 | 理由 |
| --- | --- | --- |
| 介入対象 | 自分のみ | Instagram DMに第三者Botを常駐させる公式手段が存在しないため、共同介入は技術的に不可能。同時に、片側介入は同意問題を最小化する。 |
| データ取得 | 公式エクスポート → ブラウザ拡張 | 非公式APIはアカウント停止リスクを伴い、得られる差分に見合わない。 |
| 処理 | 完全ローカル | パートナーの発言を第三者サーバへ送出しない。 |
| ベースライン | 履歴から算出した**固定定数** | 継続更新型の個人プロファイルを作らず、正規化のみ行う。 |
| 評価 | 自分の過去ログによる遡及検証 | n が十分（数万メッセージ規模）であり、実験募集を要さずに定量評価が成立する唯一の領域。 |

## 2. v1.0からの設計転回

v1.0（LINE / 双方同意 / 共同調停）から、以下を意図的に反転させた。差分を明示しておかないと、v1.0の資産を誤って再導入する危険がある。

| 論点 | v1.0 | v2.0 | 転回の理由 |
| --- | --- | --- | --- |
| 介入先 | 二人の共有チャット | 自分のみ | Instagram DMに常駐Botを置く公式手段がない |
| 同意 | 双方の明示同意（Postback） | パートナーへの開示（P0-ETH-01） | 二者間サービスではなく個人ツールのため。ただし同意原則は消滅しない |
| 調停生成 | Tier 2による共同整理 | 対象外（自分向けの短い促しのみ） | 相手に見せない以上、共同整理の意味がない |
| Safety Gate | 危険時に調停停止 | 危険時に**自己非難型の通知を停止**（P0-ETH-04） | 被害側に「あなたも落ち着いて」と言う危険を排除 |
| 長期記憶 | 派生指標の保存（PRI-008で禁止） | 履歴から一度だけ算出する固定定数 | 継続プロファイリングを回避しつつ正規化を可能にする |
| 実装言語 | TypeScript / GCP | Python / ローカル | 日本語形態素解析・統計評価・可視化の資産が厚く、サーバ運用が不要 |
| 評価 | カップル募集による前向き検証 | 自分の履歴による遡及検証 | 募集問題が消え、統計的に意味のある n が得られる |

**継承する資産**：AI-001〜009（主張と推測の分離、非審判、非診断、文脈不足の明示）、PRI-005〜008（HMAC、本文非永続化、プロファイル非永続化）、Fail Closed 原則、Version Everything 原則。

## 4. 中核仮説と成功定義

### 4.1 仮説

| ID | 仮説 | 反証条件 |
| --- | --- | --- |
| H-1 検知可能性 | 過去の対立は、対立区間の開始前後で特徴量の統計的逸脱として現れる | 対立区間と通常区間で特徴量分布が分離しない |
| H-2 先行性 | 検知時刻は、自分が対立を自覚した時刻より前に到来する | Lead Time 中央値 ≤ 0 |
| H-3 誤報許容性 | 通常会話における誤報頻度が、無視されない水準に収まる | 誤報が週3回を超える |
| H-4 行動変容 | 通知を受けた自分は、送信内容または送信タイミングを実際に変える | 通知後の自分の発話に変化が観測されない |

H-1〜H-3はPhase 1（遡及）で検証する。H-4はPhase 2でのみ検証可能であり、Phase 1のGoを条件とする。

### 4.2 North Star

| **North Star Metric** |
| --- |
| **Lead Time（分）= 自覚時刻 − 初回アラート時刻**。検知精度そのものではなく、「自分より早いか」だけを成功指標とする。アラート回数の多さは成果ではない。 |

### 4.3 受入基準（Phase 1 Gate）

遡及評価は自分の履歴全体を母集団とするため、小標本問題が生じない。したがって数値基準を設定できる（v1.0でカップル募集に対して数値Gateを撤回した判断とは、前提が異なる）。

| Gate | 合格基準 | 不合格時 |
| --- | --- | --- |
| G-A データ健全性 | mojibake復元後、日本語が正しく読める。欠損・重複・時刻逆転が既知量として説明できる | パーサ修正 |
| G-B 分離可能性 | 対立区間と通常区間で heat score の分布が分離（AUC ≥ 0.75） | 特徴量再設計 |
| G-C 先行性 | Lead Time 中央値 ≥ +10分、かつ 25パーセンタイル ≥ 0 | 閾値・窓幅の再設計。改善しなければ**プロジェクト終了** |
| G-D 誤報 | 通常会話ウィンドウ換算で 誤報 ≤ 1/200 | 閾値引き上げ、特徴量数の下限引き上げ |
| G-E 頑健性 | 直近3か月をホールドアウトした場合も G-B〜G-D を維持 | 過学習として閾値を保守側へ |

## 6. 倫理・同意・安全の不変条件

| ID | 優先 | 不変条件 | 受入基準 |
| --- | --- | --- | --- |
| P0-ETH-01 | P0 | パートナーへの開示。本システムの存在・目的・扱う範囲をパートナーへ説明済みであること。 | 実装開始前に説明を完了。未完了の場合、Phase 2（リアルタイム化）へ進まない。 |
| P0-ETH-02 | P0 | 相手向け出力の不在。相手に送信・提示される出力を生成するコードパスが存在しない。 | 送信系APIクライアントを依存関係に含めない。CIで検出。 |
| P0-ETH-03 | P0 | 相手プロファイルの非永続化。相手個人の攻撃性・感情の長期時系列を保存しない。 | 永続層に `partner_*_score` 相当の時系列カラムが存在しない。スキーマ検査で検証。 |
| P0-ETH-04 | P0 | 非難構文の禁止。通知文が「あなたが悪い」「落ち着いて」等、自己または相手への責任帰属を含まない。 | 通知テンプレートは静的定義のみ。禁止語リストによるテストを通過。 |
| P0-ETH-05 | P0 | 安全分岐。脅迫・暴力・強要・自傷他害の語彙を検知した場合、通常のヒート通知を送らず、静的な安全案内のみ表示する。 | Safety語彙テストケースで通常通知が抑止されること。 |
| P0-ETH-06 | P0 | ローカル完結。会話本文がネットワークへ送出されない（OPT-201の明示的有効化時を除く）。 | 通信を伴うライブラリを解析層に持ち込まない。オフライン実行テストを通過。 |
| P0-ETH-07 | P0 | 反芻の抑制。関係性の良否を示す常設スコア・スコア推移グラフを日常的に提示しない。 | UIに常設ダッシュボードを実装しない。校正レポートは明示コマンド実行時のみ生成。 |
| P1-ETH-08 | P1 | 停止容易性。単一のコマンドまたはトグルで全通知を即時停止できる。 | Kill Switch のE2Eテスト。 |
| P1-ETH-09 | P1 | 削除容易性。単一コマンドで全派生データと本文キャッシュを削除できる。 | 削除後にセンチネル文字列が残存しないことを検証。 |

### 6.1 P0-ETH-04・05の設計意図

自己監視型は、**利用者自身が被害側である場合に危険な出力を出しうる**。相手の攻撃性が上昇している局面で「あなたも一呼吸を」と促すことは、非対称な関係において自己抑制を強化し、状況を悪化させる。したがって通知は常に**状態の記述**にとどめ、行動の指示を含めない。

- 許容：「直近25分、応酬が速くなっています。」
- 許容：「普段より短文・高頻度の往復が続いています。」
- 禁止：「感情的になっています。落ち着いてから返信しましょう。」
- 禁止：「相手を責める表現が増えています。」

## 7. データソース仕様（Instagram Export）

### 7.1 取得

Metaの「アカウントセンター → 自分の情報をダウンロード」から、**JSON形式**でメッセージを要求する。HTML形式は解析に不向きのため選択しない。生成には数時間〜数日を要する。

### 7.2 想定構造

```
your_instagram_activity/messages/inbox/<thread_slug>_<id>/
  ├─ message_1.json      # 長いスレッドは _2, _3 ... へ分割される
  ├─ photos/ videos/ audio/
```

```jsonc
{
  "participants": [{ "name": "..." }, { "name": "..." }],
  "messages": [
    {
      "sender_name": "...",
      "timestamp_ms": 1750000000000,
      "content": "...",                    // 任意。存在しない場合がある
      "reactions": [{ "reaction": "...", "actor": "..." }],
      "share": { "link": "..." },          // 任意
      "photos": [{ "uri": "..." }],        // 任意
      "is_geoblocked_for_viewer": false
    }
  ],
  "title": "...",
  "thread_path": "inbox/..."
}
```

### 7.3 既知の落とし穴（FR-101で必ず対処）

| ID | 事象 | 対処 |
| --- | --- | --- |
| PIT-01 | **文字化け（最重要）**：UTF-8バイト列がLatin-1として解釈された状態で格納される。日本語・絵文字が全て破損して見える | 各文字列に `s.encode('latin-1').decode('utf-8')` を適用。失敗時は原文を保持し、失敗率をレポートに記録 |
| PIT-02 | メッセージ配列は**新しい順**（降順） | 読み込み後に昇順ソートを強制 |
| PIT-03 | ファイル分割 | `message_*.json` を全件読み、連結後に重複除去（`timestamp_ms` + `sender_name` + `content` のハッシュ） |
| PIT-04 | `content` 欠損 | 写真・スタンプ・シェア・通話・取消のいずれか。`message_type` を導出し、テキスト特徴量からは除外、頻度特徴量には算入 |
| PIT-05 | システム文 | 「〜さんがいいね！しました」「通話時間」等の自動生成文を除外リストで判定 |
| PIT-06 | 同一ミリ秒の複数件 | 安定ソートのため元順序を副キーとして保持 |
| PIT-07 | エクスポート範囲の欠落 | 「消えるメッセージ」「削除済み」は含まれない。母集団の偏りとしてレポートに明記 |

### 7.4 データ取扱い

| ID | 優先 | 要件 |
| --- | --- | --- |
| DAT-101 | P0 | エクスポートZIPおよび展開物は、クラウド同期対象外のディレクトリ（`~/heatwatch-data/` 等）に置く。リポジトリ配下に置かない。 |
| DAT-102 | P0 | `.gitignore` に データディレクトリ・`*.json` 実データ・`.env` を含める。CIでコミット混入を検査する。 |
| DAT-103 | P1 | 派生データ（特徴量・ラベル・評価結果）のみをローカルSQLiteに保存する。本文は保存しない。 |
| DAT-104 | P1 | 解析中の本文はプロセスメモリ上のみで扱う。ログ・例外メッセージ・トレースに本文を出力しない。 |

## 8. データモデル

### 8.1 中間表現（メモリ内）

```python
@dataclass(frozen=True)
class Message:
    idx: int                 # 昇順の連番
    ts: datetime             # tz-aware（Asia/Tokyo）
    speaker: Literal["SELF", "PARTNER"]   # 実名を保持しない
    text: str | None         # 復元済み本文。メモリ内のみ
    msg_type: MessageType    # TEXT | PHOTO | STICKER | SHARE | CALL | SYSTEM | UNSENT
    char_count: int
    reaction_count: int
```

### 8.2 永続層（SQLite、本文禁止）

| テーブル | 主要列 | 注記 |
| --- | --- | --- |
| `windows` | id, start_ts, end_ts, msg_count, feature_version | 解析単位 |
| `features` | window_id, name, raw_value, z_value | 特徴量の値のみ。本文なし |
| `scores` | window_id, heat_score, level, threshold_version | 検知結果 |
| `labels` | interval_id, start_ts, end_ts, kind, aware_ts, source | 手動ラベル（§12.2） |
| `evaluations` | run_id, config_hash, auc, lead_time_p50, fp_rate, created_at | 評価結果 |
| `baseline` | feature_name, mean, std, p50, p90, computed_at, sample_n | 固定定数（DEC-106） |
| `alerts` | ts, level, template_id, acknowledged | Phase 2。本文・引用を含めない |

**禁止列**：本文、実名、相手個人の時系列スコア、関係性総合スコア。

## 9. 特徴量仕様

### 9.1 理論的アンカー

Gottmanの「四騎士」（批判・侮辱・防衛・逃避）と修復試行（repair attempt）を観測可能な代理変数へ写像する。v1.0の特徴量群は理論的根拠が弱く、恣意的な重み付けに陥っていたため、本書では出典を持つ枠組みに接続する。ただしこれは**臨床的診断ではなく検知のための特徴設計**であり、解釈をユーザーへ提示しない（P0-ETH-04）。

### 9.2 特徴量定義

| ID | 特徴量 | 対応理論 | 計算 | 正規化 |
| --- | --- | --- | --- | --- |

## 10. 検知エンジン仕様

### 10.1 スコアリング

```
heat_raw = Σ (w_i × f_i)  −  w_repair × F-07
heat_score = clamp(heat_raw, 0, 1)
```

初期重みは仮説であり、§12の遡及評価で校正する。重みは `config/weights.yaml` に置き、`threshold_version` として記録する。

### 10.2 発火条件

```
eligible =
     window.msg_count >= 6
  && window.both_speakers
  && !cooldown.active
  && !kill_switch
  && active_feature_count >= 2          # 単一特徴で鳴らさない

trigger =
     eligible
  && heat_score >= threshold.enter
  && slope(heat_score, last_3_windows) >= threshold.min_slope
  && sustained_ms >= 90_000

exit = heat_score < threshold.exit      # ヒステリシス
```

| ID | 優先 | 要件 |
| --- | --- | --- |
| DET-101 | P1 | ヒステリシス（enter > exit）により、閾値付近での連続発火を抑制する。 |
| DET-102 | P1 | クールダウンを既定90分とし、同一対立での再通知を抑制する。設定可能。 |
| DET-103 | P1 | 1日あたりの通知上限を既定3回とする。超過分は抑制し、抑制件数のみ記録する。 |
| DET-104 | P0 | Safety語彙検知時は §6 P0-ETH-05 に従い通常通知を抑止する（Fail Closed）。 |
| DET-105 | P1 | 全スコアに `feature_version` / `threshold_version` / `baseline_version` を付与して記録する。 |
| DET-106 | P1 | オンライン学習を行わない。閾値・重みの変更は明示的な再校正コマンドのみ。 |

## 12. 評価・校正プロトコル

**本書で最も重要な章である。** 実装の目的は、この評価を実行可能にすることにある。

### 12.1 データ分割

| 区分 | 範囲 | 用途 |
| --- | --- | --- |
| 校正セット | 履歴の古い側 70% | 重み・閾値の校正、ベースライン算出 |
| ホールドアウト | 直近 30%（時系列で分割） | 最終評価。**校正に一切用いない** |

ランダム分割を禁止する。同一対立区間が両側に跨ると評価が汚染されるため、時系列分割のみを用いる。

### 12.2 ラベリング（操作的定義）

後知恵バイアスを避けるため、記憶ではなく**ログ上の客観的基準**でラベル時刻を決める。

| ラベル | 定義 |
| --- | --- |
| `conflict_start` | 事後的に見て、対立の連鎖が始まったと判断できる最初のメッセージ |
| `aware_ts` | **自分が対立を明示的に言語化した最初の自分の発話**（例：「なんで怒ってるの」「それは違うと思う」「ちょっと話そう」）。記憶による推定を用いない |
| `conflict_end` | 修復発話の後、24時間以内に対立語彙の再出現がない時点 |
| `normal` | 上記いずれにも属さない区間 |

| ID | 優先 | 要件 |
| --- | --- | --- |
| EVA-101 | P1 | ラベリング支援CLIを実装する。時系列を表示し、区間の開始・終了・aware_tsを対話的に記録する。 |
| EVA-102 | P1 | 同一期間を2回、最低1週間の間隔を空けてラベリングし、`aware_ts` の一致度（±5分以内の一致率）を記録する（OQ-103）。 |
| EVA-103 | P1 | ラベルは本文を含まず、時刻と区間種別のみを保存する。 |

### 12.3 指標

| 指標 | 定義 |
| --- | --- |
| **Lead Time** | `aware_ts − first_alert_ts`（分）。正なら自分より早い。対立ごとに算出し、中央値と25/75パーセンタイルを報告 |
| Detection Rate | ラベル済み対立のうち、`conflict_end` 以前にアラートが発生した割合 |
| False Alert Rate | `normal` 区間における発火数 / 通常ウィンドウ数 |
| AUC | 窓単位での対立/通常の分離度 |
| Time-to-Detect | `conflict_start → first_alert` の経過時間 |

### 12.4 校正手順

1. ベースラインを `normal` 区間のみから算出する（対立区間を含めると正規化が破綻する）。
2. 校正セットで重みを探索する。探索空間は粗いグリッドに限定し、過剰最適化を避ける。
3. Lead Time を目的関数とし、False Alert Rate を制約条件とする（精度ではなく先行性の最大化）。
4. ホールドアウトで一度だけ評価する。基準未達の場合、閾値のみを保守側へ調整し、**特徴量の再設計はホールドアウトを見ずに行う**。
5. 校正レポート（Markdown + 図）を `reports/` に出力する。

| ID | 優先 | 要件 |
| --- | --- | --- |
| EVA-104 | P1 | 評価は単一コマンド（`heatwatch evaluate`）で再現可能とし、`config_hash` を結果に記録する。 |
| EVA-105 | P1 | 校正レポートに、Lead Time分布・特徴量重要度・誤報事例の時刻一覧（本文なし）を含める。 |
| EVA-106 | P0 | ホールドアウトでの評価回数を記録し、3回を超えた場合は警告する（多重検定による自己欺瞞の防止）。 |

## 14. Phase 2：準リアルタイム化

**Phase 1のGate G-C合格を前提条件とする。** 未合格の場合は着手しない。

| ID | 優先 | 要件 |
| --- | --- | --- |
| RT-101 | P1 | Chrome拡張（Manifest V3）が Instagram Web のDMスレッドを監視し、MutationObserverで新着を検出する。 |
| RT-102 | P1 | 拡張は `127.0.0.1` のローカルAPI（FastAPI）へのみ送信する。外部ホストへの送信先を持たない。 |
| RT-103 | P0 | 拡張はDOMの読み取りのみを行い、送信・既読・いいね等の書き込み操作を一切行わない。 |
| RT-104 | P1 | DOM構造変更に対する耐性として、セレクタを設定ファイルへ外出しし、取得失敗を検知して通知する。 |
| RT-105 | P1 | ローカルAPIは受信本文をメモリ上のウィンドウにのみ保持し、TTL 60分で破棄する。 |
| RT-106 | P1 | 拡張の有効/無効、Kill Switchをブラウザのポップアップから切り替えられる。 |
| RT-107 | P2 | 取りこぼし対策として、定期的なエクスポート再取り込みで欠損を補完できる。 |

| **DOM依存の脆弱性** |
| --- |
| Instagram Webの構造は予告なく変更される。RT-104の失敗検知がない場合、「鳴らないこと」を「平穏」と誤認する。**サイレント故障が本システム最大の運用リスクである。** ヘルスチェック（一定時間メッセージ取得がない場合の自己通知）をP1とする。 |
